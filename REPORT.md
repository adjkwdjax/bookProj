# Отчет о проектировании и реализации проекта
## 1. Архитектура

В проекте можно выделить три основных уровня.

### Фронтенд

Интерфейс реализован на Next.js с app router. В проекте присутствуют страницы для авторизации, регистрации, каталога книг, просмотра карточки книги, создания и редактирования книг, оформления заказа, профиля пользователя и административных разделов.

### API-слой

Серверная логика сосредоточена в маршрутах `app/api/*`. Через эти маршруты выполняются регистрация и вход, работа с профилем, создание и обработка предложений, оформление транзакций, получение уведомлений и административные операции.

### Слой данных

Работа с PostgreSQL вынесена в `src/lib/db.postgres.ts`. Этот модуль отвечает за подключение к базе, выполнение запросов, транзакции, инициализацию схемы и заполнение начальными данными.

## 2. Планирование реализации
 
## Стек технологий

- **Фреймворк:** Next.js (app router) - серверные маршруты и рендеринг.
- **Язык:** TypeScript для типобезопасности на фронтенде и сервере.
- **UI:** React 18/19 (в связке с Next.js) и Tailwind CSS для стилизации.
- **База данных:** PostgreSQL с использованием `pg` (node-postgres); используются расширения, например `pgcrypto`.
- **Валидация:** `zod` для схем входных данных и валидации API.
- **Идентификаторы:** UUID (`uuid`), первичные ключи в БД - `uuid`.
- **Состояние/стор:** `zustand` в клиентском приложении.
- **HTTP/запросы:** `axios` для клиентских вызовов API (где применяется).
- **Инструменты разработки:** TypeScript, Node.js.


План проекта строился последовательно.

Сначала была определена предметная область: пользователи, книги, категории, предложения, транзакции, платежи и уведомления. После этого была выбрана реляционная модель хранения, поскольку она лучше всего подходит для связанных сущностей и строгой целостности данных.

Затем была сформирована структура таблиц и типизация. Для ключевых статусов и ролей использованы enum-типы PostgreSQL и TypeScript, чтобы значения в коде и в базе совпадали.

После этого был определён способ автоматической инициализации базы. В проекте предусмотрены создание типов, таблиц, индексов и seed-данных, чтобы приложение могло запускаться на чистой базе.

На следующем этапе была описана логика серверных маршрутов: регистрация, каталог книг, предложения, транзакции, уведомления, профиль и административные действия.

## 3. Реализация базы данных

База данных построена как набор взаимосвязанных таблиц.

### Основные таблицы

- `users` — пользователи, их роли, признак блокировки, аватар и базовые данные.
- `categories` — категории книг и связь с модераторами.
- `books` — книги с названием, автором, описанием, изображением, категорией и владельцем.
- `offers` — предложения по продаже, аренде или обмену.
- `transactions` — записи о сделках между покупателем и продавцом.
- `payments` — сведения о платежах по транзакциям.
- `notifications` — уведомления, связанные с действиями в системе.

### Формат идентификаторов и статусов

Для первичных ключей используется UUID. Такой подход подходит для распределённой среды и снижает зависимость от последовательных числовых id.

В схеме определены собственные перечисления для ролей и статусов. Это помогает избежать ситуаций, когда приложение передаёт в базу значение, которого нет в разрешённом списке.

### Начальные данные

Для разработки и тестирования в базе предусмотрены начальные записи: администратор, модератор, обычный пользователь, несколько категорий, книг, предложений и уведомлений. Все идентификаторы приведены к UUID-формату, чтобы соответствовать типам столбцов.

## 4. Реализация серверной логики

Серверные маршруты работают с PostgreSQL напрямую через общий helper.

### Регистрация и авторизация

При регистрации проверяется уникальность email, создаётся пользователь с UUID и формируется токен авторизации. Авторизация и базовые пользовательские данные возвращаются через API в согласованном формате.

### Каталог и карточки книг

Маршруты, связанные с книгами, работают через таблицу `books`. Поддерживаются просмотр списка, чтение карточки, создание и редактирование записи.

### Предложения и транзакции

Предложения хранятся в `offers`, транзакции — в `transactions`. При оформлении заказа используется телефон покупателя, поскольку он требуется продавцу для связи.

### Профиль и уведомления

Профиль пользователя хранит и возвращает данные, необходимые для отображения состояния аккаунта и связанных транзакций. Уведомления используются для фиксации значимых событий в системе.

### Административные возможности

Для администратора и модератора предусмотрены отдельные маршруты, связанные с пользователями, книгами, категориями и статусами контента.

## 5. Реализация интерфейса

Интерфейс приложения соответствует серверной логике и структуре данных.

На странице оформления заказа отображается форма, включающая телефон покупателя. На странице профиля показываются данные, полезные для участника сделки, включая контактную информацию в контексте транзакции.

Формы и страницы связаны с API через стандартные запросы, а состояние компонентов строится на данных, полученных с сервера.

## 6. Проверка корректности

В проекте важна согласованность между кодом и БД, поэтому проверяются несколько аспектов:

- соответствие UUID-формата для ключевых полей;
- совпадение enum-значений в коде и в PostgreSQL;
- корректность SQL-инициализации;
- отсутствие синтаксических ошибок в TypeScript;
- соответствие API-данных структуре таблиц.

В проекте используется автоинициализация схемы, поэтому при старте приложения база может быть подготовлена автоматически.

## 7. Текущий результат

На текущий момент проект представляет собой полноценное Next.js-приложение с PostgreSQL в роли основной базы данных. В системе доступны:

- регистрация и авторизация пользователей;
- каталог и карточки книг;
- создание предложений;
- оформление транзакций;
- хранение данных о платеже и статусе сделки;
- уведомления;
- административные маршруты;
- единая типизация данных на уровне кода и БД.
